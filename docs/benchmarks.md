## Baseline (P0.6)

Generated by `zig build bench`, which builds `src/bench.zig` in ReleaseSafe and ReleaseFast.
The DOD targets (plan §9) are measured against these numbers in ReleaseSafe. "Steps" are the old
runtime's `step()` calls, so steps/s is not comparable with the new VM's instructions/s; turns/s
and lines/s are. "Runtime objects" are the old `RuntimeObject`s in all containers, the closest
thing to instructions.

The new runtime's sections (`bench-new`) play ink's JSON of the same two stories with the same
seeded choices, so turns/s and lines/s compare with the old runtime's; its memory is the
program plus the state's fixed budget at the default limits, so bytes per instruction is high
for a small story and falls as stories grow.

## Memory budget sizing (P4.12)

A story's runtime state is one allocation of exactly `Limits.bytes_total(shape)` bytes, made by
`Story.init` (tested with a counting allocator in `src/vm/state.zig`). Nothing allocates after
that. The total has three parts:

- **Live flow**: the evaluation stack, call stack (frames, threads, temps), output items and
  `str` marks, and the choices with their tags and thread snapshots.
- **Lookahead**: a second copy of the live-flow buffers for the newline lookahead (plan §4.6),
  plus the undo log (`patch_entries_max` × 16 bytes).
- **Shared**: globals and their defaults (24 bytes each), visit counts and turn indices
  (8 bytes per counted container), the line buffer (`output_bytes_max`), the string heap, the
  list slab, the flow directory (64 bytes per flow), the flow parking region, observers, the
  observer queue, errors and warnings, the ancestor scratch for visit counting, and the
  scratch `load_json` tokenizes a save into (16 bytes per token, `load_nodes_max`).

Flows don't multiply the budget: all flows of a story share one state, and only the current
flow uses the live buffers. A switched-out flow is packed into the parking region, taking
44 bytes of header plus what it actually uses: 24 bytes per frame, 20 per thread, 16 per
temp, 12 per output item, 40 per choice, 24 per choice snapshot, 4 per tag or mark. A flow
waiting at a choice, three frames deep, with 10 temps, 20 output items and 4 choices with
their snapshots, parks in about 1 KiB, so the default 256 KiB parking region holds hundreds.

### Example: one main story and four side stories

The numbers are pinned by the test "the sizing example in docs/benchmarks.md" in
`src/core/limits.zig`; change them together.

- **Main story**: default limits with `flows_max = 4` (the main thread plus three ambient or
  companion flows), 3000 counted containers, 200 globals.
- **Side stories** (barks, a shop, a codex): `small_story_limits` in `src/core/limits.zig`,
  each with 300 counted containers and 30 globals and up to four flows. These limits cut the
  heap to 64 KiB, the call stack to 128 frames and choices to 16.

| Part | Main story | Side story |
|---|---:|---:|
| Live flow | 180,736 | 27,776 |
| Lookahead (copy + undo log) | 197,120 | 31,872 |
| Shared | 1,738,112 | 180,784 |
| **Total per story** | **2,115,968** (2.02 MiB) | **240,432** (235 KiB) |

The whole game, one main story and four side stories, needs 2,115,968 + 4 × 240,432 =
3,077,696 bytes (2.94 MiB), fixed at load time. In the main story the 1 MiB string heap is
about half of the total. It is the first limit to tune: measure the heap's high-water
mark over a full playthrough, double it, and round up.

## Weave heuristics (P0.12)

Generated by `zig build heuristics-report`: how often each old-runtime weave heuristic changed
control flow per ground-truth case, with the case's own actions and three seeded random choice
policies, split by compiler ("ink compiler" is the old runtime on ink v1.2.1's JSON, "old
compiler" is the old compiler on the old runtime).

What it means for P5.2 (measured 2026-11-11):

- `loopBackGatherTailPeel` never fires on any case. It is likely dead code; P5.2 needs no
  replacement for it unless a reproduction turns up.
- `divertTargetsAncestorOfAnyChoiceSource` fires on three weave cases, equally for both
  compilers. It compensates for a runtime gap, not for old-compiler output, so the fix
  belongs in the new VM's weave semantics (thread and gather handling), not in the compiler.
