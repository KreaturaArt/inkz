## Baseline (P0.6)

Generated by `zig build bench`, which builds `src/bench.zig` in ReleaseSafe and ReleaseFast.
The DOD targets (plan §9) are measured against these numbers in ReleaseSafe. "Steps" are the old
runtime's `step()` calls, so steps/s is not comparable with the new VM's instructions/s; turns/s
and lines/s are. "Runtime objects" are the old `RuntimeObject`s in all containers, the closest
thing to instructions.

The new runtime's sections (`bench-new`) play ink's JSON of the same two stories with the same
seeded choices, so turns/s and lines/s compare with the old runtime's; its memory is the
program plus the state's fixed budget at the default limits, so bytes per instruction is high
for a small story and falls as stories grow.

The compiler sections (`bench-compile`, P8.6) compile both stories from source to JSON with
the old compiler and with the new one (`src/compiler`, a faithful port of ink's
compiler): mean time and peak allocated bytes. The new compiler peaks at less than half the
old one's memory: its parse workspace is sized from the source length (doubled on at most
`compile_retries_max` retries) and settled to what the parse used, and the object tree, the
resolution and the syntax are freed once the IR is lowered, before layout and emission. It is
slower than the old compiler, which skips most of ink's semantics (weave, resolution and
validation passes); compile speed is not a P8.6 target.

## Memory budget sizing (P4.12)

A story's runtime state is one allocation of exactly `Limits.bytes_total(shape)` bytes, made by
`Story.init` (tested with a counting allocator in `src/vm/state.zig`). Nothing allocates after
that. The total has three parts:

- **Live flow**: the evaluation stack, call stack (frames, threads, temps), output items and
  `str` marks, and the choices with their tags and thread snapshots.
- **Lookahead**: a second copy of the live-flow buffers for the newline lookahead (plan §4.6),
  plus the undo log (`patch_entries_max` × 16 bytes).
- **Shared**: globals and their defaults (24 bytes each), visit counts and turn indices
  (8 bytes per counted container), the line buffer (`output_bytes_max`), the cleaned-text
  cache (`output_items_max` × 12 bytes plus `output_bytes_max`, P10.1), the string heap, the
  list slab, the flow directory (64 bytes per flow), the flow parking region, observers, the
  observer queue, errors and warnings, the ancestor scratch for visit counting, and the
  scratch `load_json` tokenizes a save into (16 bytes per token, `load_nodes_max`).

Flows don't multiply the budget: all flows of a story share one state, and only the current
flow uses the live buffers. A switched-out flow is packed into the parking region, taking
44 bytes of header plus what it actually uses: 24 bytes per frame, 20 per thread, 16 per
temp, 12 per output item, 40 per choice, 24 per choice snapshot, 4 per tag or mark. A flow
waiting at a choice, three frames deep, with 10 temps, 20 output items and 4 choices with
their snapshots, parks in about 1 KiB, so the default 256 KiB parking region holds hundreds.

### Example: one main story and four side stories

The numbers are pinned by the test "the sizing example in docs/benchmarks.md" in
`src/core/limits.zig`; change them together.

- **Main story**: default limits with `flows_max = 4` (the main thread plus three ambient or
  companion flows), 3000 counted containers, 200 globals.
- **Side stories** (barks, a shop, a codex): `small_story_limits` in `src/core/limits.zig`,
  each with 300 counted containers and 30 globals and up to four flows. These limits cut the
  heap to 64 KiB, the call stack to 128 frames and choices to 16.

| Part | Main story | Side story |
|---|---:|---:|
| Live flow | 180,736 | 27,776 |
| Lookahead (copy + undo log) | 197,120 | 31,872 |
| Shared | 1,852,800 | 195,120 |
| **Total per story** | **2,230,656** (2.13 MiB) | **254,768** (249 KiB) |

The whole game, one main story and four side stories, needs 2,115,968 + 4 × 240,432 =
3,077,696 bytes (2.94 MiB), fixed at load time. In the main story the 1 MiB string heap is
about half of the total. It is the first limit to tune: measure the heap's high-water
mark over a full playthrough, double it, and round up.

## Final report (P9.4)

The generated sections above hold the latest run. On this machine, run-to-run variation is large: the same commit measured up to 1.7× apart on different runs of the same day. So the ratios below compare the old and new runtimes measured **in the same run** (the last bench run before P9.1 deleted the old runtime, commit 2091249). The P0.6 baseline sections (commit 88ae377) are kept above unchanged.

### Plan §9 benchmark targets (ReleaseSafe)

| Target | crime_scene | generated (1000 knots) | Result |
|---|---|---|---|
| `cont()` throughput ≥ 3× (turns/s; the old `cont()` returned a whole turn) | 20,849 → 61,031 (2.9×) | 23,658 → 310,228 (13.1×) | met on the large story; just short on crime_scene |
| Load ≥ 2× faster | 392 µs → 632 µs (0.6×) | 8,169 µs → 6,350 µs (1.3×) | not met |
| Compiler peak memory ≥ 2× lower | 535,918 → 246,873 B (2.17×) | 13,067,678 → 4,753,137 B (2.75×) | met |

The same comparisons in ReleaseFast:

| Measurement | crime_scene | generated (1000 knots) |
|---|---|---|
| Turns/s | 3.97× | 17.2× |
| Lines/s | 1.94× | 8.6× |
| Load time | 0.92× (slower) | 1.15× faster |
| Compiler peak memory | 2.30× lower | 2.95× lower |

**Shortfalls and their causes**

- **Load.** Measured in ReleaseSafe, with 200 runs each:

  | Step | crime_scene | generated |
  |---|---|---|
  | `ink_json.load` (JSON to Program) | 401 µs | 6,199 µs |
  | `Story.init` | 315 µs | 282 µs |

  - `ink_json.load` alone takes as long as the old runtime's whole load. It validates the JSON, builds the program image and computes paths and hashes, where the old runtime built its object tree directly.
  - `Story.init` allocates the state's fixed budget once (2.1 MB with the default `Limits`, plan §4.6). That cost doesn't grow with the story, so it dominates small stories.
  - A smaller `Limits`, sized from the story (see "Memory budget sizing" above), shrinks the init cost.
  - The loader was not optimised for speed, beyond the peak memory checked in P3.
- **`cont()` on crime_scene: 2.9× instead of 3×.** `cont()` now returns one line at a time with ink's newline lookahead (D12). Each line needs a snapshot and a check of the next content for glue, which the old turn-based `cont()` didn't do. On a short-lined story like crime_scene, that per-line work weighs most. This was not profiled further; on the large story the same code is 13× faster.
- **Compile time** has no target. The new compiler is 7–8× slower than the old one, which skipped most of ink's semantics (TASK-148.6).
